# Транспорти й авторизація

Код — `task_manager.py` (запуск, bearer-мідлварь, сторінка входу) і `tasks_oauth.py` (OAuth-сервер).
Змінні оточення — [config.md](config.md).

## Три транспорти

| Режим | Як увімкнути | Порт за замовчуванням | Автентифікація |
|---|---|---|---|
| stdio | за замовчуванням | — | немає (локальний процес) |
| http + bearer | `TASKS_TRANSPORT=http` або `--http` першим аргументом | `8792` | `TASKS_TOKEN` (і необовʼязковий `TASKS_ELF_TOKEN`) |
| OAuth | `TASKS_TRANSPORT=oauth` або `--oauth` | `8793` | OAuth 2.1 |

MCP-ендпоінт обох HTTP-режимів — шлях `TASKS_HTTP_PATH` (за замовчуванням `/tasks`); хост —
`TASKS_HTTP_HOST` (за замовчуванням `127.0.0.1`), порт — `TASKS_HTTP_PORT`. Скоуп OAuth — `tasks`.
Веб-дашборд реєструється в усіх режимах, крім OAuth — див. [dashboard.md](dashboard.md).

### Bearer

- Без `TASKS_TOKEN` процес завершується з повідомленням.
- Bearer вимагається **лише на MCP-шляху** (`TASKS_HTTP_PATH` і вкладені); без заголовка чи з чужим
  токеном → `401 {"error": "unauthorized"}`. Інші шляхи (дашборд, `/api/*`) заголовка не вимагають.
- Токени порівнюються за постійний час (`hmac.compare_digest`).
- Обмежений токен `elf` — [tools.md](tools.md#права-токена-elf).

### Захист від DNS-rebinding

HTTP-режими використовують перевірку заголовка `Host` з MCP SDK. Дозволені хости: `127.0.0.1`, `localhost`
(з портом і без) плюс `TASKS_ALLOWED_HOSTS` (через кому). Для OAuth-інстансу за публічним іменем
`TASKS_ALLOWED_HOSTS` обовʼязковий: інакше запит із зовнішнього імені відбивається відповіддю
`421 Misdirected Request` (`Invalid Host header`), і клієнт зациклюється на логіні. `Origin`: дозволено
`*` плюс `TASKS_ALLOWED_ORIGINS`.

## OAuth-сервер

`TasksOAuthProvider` реалізує інтерфейс `OAuthAuthorizationServerProvider` з MCP SDK 2.x для одного
користувача.

- **Динамічна реєстрація клієнтів (DCR)**: клієнт реєструється сам; приймаються лише дозволені
  `redirect_uri` (нижче).
- **Authorization code + PKCE**. Крок авторизації веде на власну сторінку `/login?rid=…`: код видається
  лише після правильного пароля. Сторінка показує екран згоди: назву клієнта, хост, куди піде код, і час
  реєстрації клієнта (клієнти, зареєстровані менше доби тому, позначені як нові). Невідомий чи
  застарілий `rid` форму не показує.
- **Пароль**: `TASKS_OAUTH_PASSWORD_HASH` — рядок `pbkdf2_sha256$<ітерації>$<сіль hex>$<хеш hex>`
  (генерується `tasks_oauth.hash_password`, 600 000 ітерацій за замовчуванням, див. приклад у
  `.env.example`). Запасний варіант для сумісності — відкритий `TASKS_OAUTH_PASSWORD`, але лише якщо
  хеш не заданий. Без жодного з них OAuth-інстанс не стартує. Перевірка — за постійний час.
- **Ліміт спроб входу** глобальний (за reverse-проксі реальний IP клієнта не видно): 5 невдалих спроб
  підряд блокують вхід на 15 хвилин (`429`); успішний вхід скидає лічильник.
- **Заголовки сторінки входу**: `Content-Security-Policy` без скриптів і фреймів, `X-Content-Type-Options:
  nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`. Форма постить на відносну адресу
  `login`, щоб працювати за проксі, який зрізає зовнішній префікс `/tasks`.
- **Строки життя**: код авторизації — 5 хв, access-токен — 1 год, refresh-токен — 30 днів. Refresh
  ротується: використаний refresh-токен видаляється, видається нова пара.
- **Привʼязка до ресурсу (RFC 8707)**: токени привʼязані до `TASKS_RESOURCE_URL` і мають scope рівно
  `tasks`; `authorize` і обмін кодів/refresh-токенів із чужим `resource` чи scope відхиляються
  (`invalid_target`, `invalid_scope`). Refresh без розширення scope.
- **`ResourceGuard`** — ASGI-мідлварь на `POST /token`: перевіряє параметр `resource` (якщо він є, він має
  дорівнювати ресурсу сервера, інакше `400 invalid_target`), тіло понад 64 КіБ → `413`; далі віддає
  запит SDK без змін.
- **Стан** (клієнти, access- і refresh-токени) — `oauth_state.json` у `TASKS_STATE_DIR` (без змінної —
  `.oauth_state.json` поруч із кодом); пишеться атомарно, права `0600` (каталог створюється з `0700`).
  На старті прострочені токени й токени без `resource` (legacy) або з іншим ресурсом/scope вичищаються:
  після оновлення з версії без привʼязки до ресурсу конектори треба перелогінити один раз.
- `TASKS_ISSUER_URL` — публічний issuer (за замовчуванням `http://localhost:8793`); `TASKS_RESOURCE_URL`
  за замовчуванням дорівнює issuer, якщо той закінчується на `/tasks`, інакше — issuer + `/tasks`.

### Allowlist `redirect_uri`

Код авторизації віддається лише на дозволені адреси. Запис списку — одне з:

- точна адреса;
- адреса, що закінчується на `/*` — у кінці рівно один сегмент-ID (`[A-Za-z0-9_-]`, до 128 символів);
- `loopback` — `http://127.0.0.1`, `http://localhost` або `http://[::1]` на будь-якому порту
  (CLI-логін).

Адреси порівнюються за розібраними частинами (схема, хост, порт, query, шлях), а не рядком; адреси з
логіном/паролем у URL, з фрагментом чи без хоста відхиляються.

Типовий список заданий у `tasks_oauth.py` (`DEFAULT_REDIRECT_ALLOWLIST`). Перевизначення без зміни коду —
`TASKS_REDIRECT_ALLOWLIST` (записи через кому); непорожнє значення **замінює** типовий список повністю.

Клієнт, чиї `redirect_uri` не проходять перевірку, не може зареєструватися (`invalid_redirect_uri`, подія
`register_rejected`). Уже збережені клієнти поза списком лишаються в стейті, але для сервера не існують
(ні authorize, ні token, ні refresh); на старті в журнал іде попередження з назвою клієнта й хостом.
Відкат — зміна змінної оточення.

## Журнал аудиту OAuth (`OAUTH_AUDIT`)

Окремий логер пише в stderr (під systemd — у journald) рядки виду:

```
OAUTH_AUDIT event=<подія> user=<користувач або -> client='<назва>' client_id=<перші 8 символів> redirect=<хост+шлях>
```

Читати: `journalctl -u <юніт OAuth-інстансу> | grep OAUTH_AUDIT`.

| Подія | Коли |
|---|---|
| `register` | клієнт зареєструвався |
| `register_rejected` | реєстрацію відхилено через `redirect_uri` поза allowlist |
| `login` | вдалий вхід паролем (код авторизації видано) |
| `login_failed` | неправильний пароль |
| `login_locked` | спроба входу під час блокування |
| `refresh` | обмін refresh-токена |

Журнал не містить токенів, кодів авторизації й `rid`; назва клієнта обрізається до 40 символів.

## Підключення клієнтів

Один OAuth-ендпоінт `https://<host>/tasks` для всіх OAuth-клієнтів (DCR + PKCE, вхід паролем):

- **ChatGPT** (web): Settings → Developer mode → Apps → створити застосунок, URL `https://<host>/tasks`,
  автентифікація **OAuth** (клієнт реєструється сам) → форма пароля. Іконка —
  [`assets/task-manager-icon.png`](../assets/task-manager-icon.png). Після зміни набору тулів — оновити
  застосунок у налаштуваннях і почати новий чат.
- **Claude** (claude.ai та мобільний застосунок): Settings → Connectors → Add custom connector → той самий
  URL.

Мітка клієнта в [журналі змін](history.md) береться з назви, під якою клієнт зареєструвався (`claude`,
`chatgpt`, …). Точні назви пунктів меню в клієнтах можуть змінюватися.
