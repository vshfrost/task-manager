# Формат даних planner

Сервіс працює над каталогом **planner** (корінь — `TASKS_PLANNER_ROOT`, див. [config.md](config.md)).
Markdown-файли — джерело правди. Парсер/серіалізатор — `planner_model.py`, операції — `planner_store.py`.

## Файли в корені planner

| Шлях | Що це | Читається як задачі? |
|---|---|---|
| `tasks.md` | глобальний список (проєкт `global`) | так |
| `projects/<слаг>.md` | задачі проєкту | так (усі `projects/*.md`) |
| `projects/<слаг>/template.md` | шаблони задач проєкту | ні (підпапка, під `projects/*.md` не підпадає) |
| `plans/<id>.md` | план задачі | ні |
| `todo-order.json` | ручний порядок колонки To Do | ні |
| `tag-colors.json` | кольори тегів | ні |
| `projects.json` | реєстр проєктів (`create_project`) | ні |
| `elf-state.json` | стан робочого циклу Elf: лічильник невдач, PR, результат CI | ні |
| `.history/` | журнал змін, див. [history.md](history.md) | ні |

Запис файлів задач — атомарний (тимчасовий файл + `os.replace`) під `flock`. Парсер round-trip:
переписуються лише рядки-задачі, заголовки, проза й порожні рядки зберігаються як є; рядки всередині
блоків ` ``` ` / `~~~` задачами не вважаються. Нова задача вставляється перед секцією, заголовок якої
(`## …`) містить `Done` або `✅`, інакше — в кінець файлу. Якщо файлу проєкту ще нема, він створюється
із заголовком `# Задачі — <проєкт>` (для `tasks.md` — `# Tasks — глобальний список`).

## Рядок задачі

```
- [x] Текст  #домен ⏫ 📅 РРРР-ММ-ДД ⚡M [[звʼязок]] 📌[Заголовок] ^id
```

Формат сумісний з Obsidian Tasks. Порядок токенів у рядку, який пише сервіс: теги, пріоритет, дедлайн,
енергія, звʼязки, заголовок, `^id`. Парсер приймає токени в будь-якому порядку.

| Токен | Значення |
|---|---|
| `[x]` | статус (таблиця нижче) |
| текст | один рядок; перенос рядка в `add_task` / `edit_task` (MCP і дашборд) — помилка |
| `#тег` | домени (теги), можна кілька |
| `🔺` / `⏫` / `🔽` | пріоритет `asap` / `high` / `low` |
| `📅 РРРР-ММ-ДД` | дедлайн; має бути реальною календарною датою |
| `⚡S` / `⚡M` / `⚡L` | енергія |
| `[[звʼязок]]` | звʼязки (шляхи нотаток), можна кілька |
| `📌[Заголовок]` | короткий заголовок, **≤ 50 символів**, обовʼязковий при створенні (рядки без нього, зроблені руками, читаються без помилки) |
| `^id` | стабільний id (hex, 6 символів); якщо його нема, сервіс дописує його сам при першому читанні |

Заголовок нормалізується: `[` і `]` замінюються на `(` і `)`, `^` і `#` прибираються. Порожній заголовок
не приймається, а через MCP і дашборд `none` його не очищає, а дає помилку: заголовок — єдине поле, яке
не можна очистити.

## Статуси

Порядок колонок:

| Символ | Статус |
|---|---|
| `[ ]` | `backlog` |
| `[>]` | `todo` (to do) |
| `[b]` | `blockers` |
| `[/]` | `in_progress` (in progress) |
| `[r]` | `in_review` (in review) |
| `[t]` | `testing` |
| `[x]` | `done` (також читається `[X]`) |

Рядок із невідомим символом статусу не вважається задачею й лишається як є. Нові задачі завжди
створюються в `backlog`.

## Матриця переходів

Правила — `TRANSITION_SOURCES` у `planner_model.py`; діють для `move_task`, `edit_task` і дашборда.
Перехід у той самий статус не є переходом.

| У колонку | Звідки можна |
|---|---|
| `backlog` | звідки завгодно |
| `todo` | `backlog`, `testing`, `in_progress`, `in_review`, `blockers` |
| `blockers` | `backlog`, `todo`, `in_progress`, `testing` |
| `in_progress` | лише `todo` |
| `in_review` | лише `in_progress` |
| `testing` | `in_progress`, `in_review`, `blockers` |
| `done` | звідки завгодно |

Виняток: **`backlog` → `todo` дозволений стору й дашборду, але заборонений через MCP**
(`move_task` і зміна статусу в `edit_task` для будь-якого клієнта — помилка). Решта переходів
однакові в MCP і на дашборді.

Тули `elf_*` рухають задачі за власними правилами (див. [tools.md](tools.md)), а не за цією матрицею.

## WIP-ліміт

Не більше `TASKS_WIP_LIMIT` (за замовчуванням `15`) задач у `in_progress` по всьому planner. Ліміт
перевіряється при вході в `in_progress` (`move_task`, `edit_task`, `elf_claim`; на рівні стору — і `add_task` зі статусом).
`todo`, `in_review` та інші колонки без ліміту. `board` показує `N/ліміт` і позначає перевищення.

## Порядок To Do (`todo-order.json`)

Задачі To Do лежать у різних файлах, тож порядок рядків його не передає. Ручний порядок — JSON-список id
у `todo-order.json`.

- Вхід у To Do без явної позиції: з `in_progress` і `in_review` — **нагору** (позиція 1); з `testing`,
  `blockers`, `backlog` — **в кінець**.
- Явна `position` (1-based; більше за довжину — в кінець) перемагає це правило. Приймає лише
  `POST /api/task/edit` (див. [dashboard.md](dashboard.md)), і лише разом зі статусом `todo` або для задачі,
  що вже в To Do. Не ціле число чи `< 1` — помилка, нічого не пишеться. `move_task` / `edit_task` у MCP
  `position` не мають.
- Вихід із To Do і видалення задачі прибирають її id зі списку. Задача To Do, якої нема у файлі порядку
  (напр. поставлена вручну в Obsidian), стає в кінець і не губиться. Нема файлу чи він зіпсований —
  порядок порожній, задачі не губляться.
- `list_tasks(status=todo)` і колонка дашборда віддають To Do в цьому порядку, а не за пріоритетом;
  решта статусів сортується за пріоритетом (`asap` → `high` → `low` → без), потім за дедлайном.

## План задачі (`plans/<id>.md`)

Багаторядковий markdown (кроки, нотатки) в окремому файлі, а не в рядку задачі; формат рядка не змінюється.
Стор читає лише `tasks.md` і `projects/*.md`, тож `- [ ]` усередині плану задачами не стають. Файл
зберігається байт-у-байт.

- Задається: `add_task(plan=…)`, `edit_task(plan=…)`, поле «План» у діалозі дашборда.
- `edit_task`: порожній параметр — не чіпати; `none` — прибрати файл плану (у сторі порожній текст теж
  прибирає).
- Читається: `get_task` (MCP), `GET /api/task?id=…` (дашборд). У списку `GET /api/tasks` плану нема.
- `delete_task` видаляє й файл плану.
- Зміна плану пишеться в журнал як поле `plan` (було → стало).
- Розділ `## Elf` у плані: сюди дописують `comment_task` і робочий цикл `elf_*` рядки виду
  `- РРРР-ММ-ДД <текст>`. Розділу нема — створюється в кінці плану.

## Шаблони (`projects/<слаг>/template.md`)

По файлу на проєкт; рядки в тому ж форматі, що й задачі. З кожного рядка-задачі береться заголовок
(без `📌[…]` — автозаголовок із тексту, ≤ 50 символів по межі слова), текст, теги, пріоритет, енергія,
звʼязки. Щоб додати шаблон — допиши рядок. Шаблони віддає `GET /api/tasks` (поле `templates`) і показує
селект «Шаблон…» на дашборді.

## Кольори тегів (`tag-colors.json`)

`{"<тег без #>": "#RRGGBB"}`. Стор не читає його як задачі, не журналює зміни. Колір — лише `#RRGGBB`
(шість hex-цифр). Тег не мусить мати задач: колір можна задати наперед.

- `GET /api/tag-colors` → `{"tag_colors": {...}}`; той самий обʼєкт є в `GET /api/tasks`.
- `POST /api/tag-color` `{"tag": "<тег>", "color": "#12ab34"}` — поставити; `"color": null` — зняти.
  Поле `color` обовʼязкове. Не-hex (`red`, `#12345`, …) → 400, нічого не записується. Відповідь — усі кольори.

## Реєстр проєктів (`projects.json`)

`{"<слаг>": {"name": "…", "repo": "owner/name" | ""}}`. Створюється `create_project` (MCP) і
`POST /api/project` (дашборд). Слаг — малі латинські літери, цифри й дефіс, не з дефіса, не `global`,
унікальний; `repo` — порожній або `owner/name`. Проєкт без запису в реєстрі (є лише файл
`projects/<слаг>.md`) працює як і раніше; `list_projects` показує його без назви й репозиторію.
Задачі з `project=<слаг>` можна додавати й без реєстрації. Зміни реєстру в журнал задач не пишуться.
