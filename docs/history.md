# Журнал змін

Усі зміни задач пишуться в `<planner root>/.history/` (код — `planner_history.py`). Журнал append-only,
нічого не чиститься. Читається тулом `history(id?, limit)` ([tools.md](tools.md)) і
`GET /api/history` ([dashboard.md](dashboard.md)).

## Файли

| Файл | Призначення |
|---|---|
| `.history/YYYY-MM.jsonl` | по файлу на місяць, один JSON на рядок |
| `.history/.state.json` | sha256 керованих файлів задач: за ним виявляються правки повз сервіс |

Запис у журнал не має ламати саму операцію: якщо дописати рядок не вдалося (помилка файлової системи),
запис мовчки пропускається. Читання йде від свіжих місячних файлів до старих і зупиняється, щойно
набрано `limit`; зіпсовані рядки пропускаються.

## Запис

```json
{"ts": "<ISO 8601>", "op": "edit", "tool": "move_task", "id": "<id>", "file": "tasks.md",
 "client": "web", "user": "<користувач>", "changes": {"status": ["backlog", "todo"]}}
```

| Поле | Значення |
|---|---|
| `ts` | час запису, ISO 8601 з часовим поясом, до секунди |
| `op` | тип запису (нижче) |
| `tool` | тул або операція, що зробила зміну (`add_task`, `move_task`, `edit_task`, `elf_claim`, `migrate_tags`, …) |
| `id` | id задачі |
| `file` | файл задачі відносно кореня planner |
| `client` | звідки прийшла зміна |
| `user` | хто її зробив |
| `changes` | `{"поле": [було, стало]}` |
| `snapshot` | повний стан задачі (лише для `delete`) |

## Типи записів (`op`)

- `add` — задачу створено; `changes` містить лише непорожні поля у вигляді `[null, значення]`.
- `edit` — змінено поля; `changes` — лише те, що реально відрізняється. Порожній діф не записується.
- `delete` — задачу видалено; `snapshot` зберігає повний стан (з планом), бо операція незворотна.
- `external` — файл задач змінили **повз сервіс** (редактор, Obsidian, git). Стор звіряє sha256
  керованих файлів із тим, що записував сам. Поля невідомі: `tool`, `id`, `client`, `user` дорівнюють
  `-`, а `changes` = `{"sha256": [<перші 12 символів до>, <перші 12 символів після>]}`. Запис показується
  у `history` для будь-якого фільтра `id`, бо попереджає, що журнал по задачі може бути неповним.

Поля, що потрапляють у діф: `status`, `text`, `domains`, `priority`, `deadline`, `energy`, `links`,
`file`, `plan`. Заголовок (`title`) у діф не входить: зміна лише заголовка запису не створює. Тули `elf_*`
і `comment_task` додають у `changes` ще ключ `elf` (`[null, "<рядок, дописаний у план>"]`), лічильник
невдач — ключ `failures` (`[було, стало]`), `elf_ci` — `ci`.

Не журналюються: зміни `tag-colors.json`, `projects.json` (створення проєкту), `todo-order.json`.

## `client` — звідки

Це вісь «пристрій/транспорт». Значення береться в такому порядку:

1. явно виставлене джерело запиту: `web` — запити веб-дашборда; `elf` — запити з токеном `elf`;
2. на OAuth-інстансі — мітка клієнта токена: `client_name`, яким клієнт зареєструвався при динамічній
   реєстрації, у нижньому регістрі, символи поза `[a-z0-9]` стиснуті в `-`, до 20 символів
   (напр. `claude`, `chatgpt`);
3. інакше — `TASKS_CLIENT` (за замовчуванням `local`; для інстансів задається в середовищі сервісу, напр.
   мітка, що описує інстанс).

Мітка з `TASKS_CLIENT` описує **інстанс**, а один bearer-інстанс обслуговує і дашборд, і MCP; тому
дашборд перекриває її через `ContextVar` (`as_client("web")`), інакше клік у дашборді не відрізнявся б
від MCP-виклику.

## `user` — хто

`subject` з OAuth access-токена; без токена (stdio, bearer) — `TASKS_DEFAULT_USER` (за замовчуванням
`vlad`). Сервіс однокористувацький: `subject` усіх OAuth-токенів — константа `SUBJECT` (`vlad`) у
`tasks_oauth.py`. Поле пишеться вже зараз, щоб при появі інших користувачів старі записи лишалися
коректними.

У виводі `history` підпис має вигляд `користувач@клієнт`, напр. `<користувач>@chatgpt`; запис `delete` виводиться
як `🗑️ видалено: <текст>`, `external` — як `⚠️ СТОРОННЯ ПРАВКА повз сервіс`.

## Міграції журналу

`scripts/migrate_backlog.py` і `scripts/migrate_tags.py` ([development.md](development.md)) працюють із
цим каталогом; `migrate_tags.py` пише власні записи (`op: edit`, `tool: migrate_tags`).
